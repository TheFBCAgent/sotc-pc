# P1: cheap throughput

Workstream P1 from `docs/NEXT.md`, aimed at symptom #1: the cutscene runs at 12–18 fps and drops to 1–8 fps on cuts.

## 1. On-disk pipeline cache

**What shadPS4 does at 14ada48.** `pipeline_cache` turns on `Storage::DataBase`
(`video_core/cache_storage.cpp`). The setting is misleadingly named: the cache does not hold a
`VkPipelineCache` blob. It holds the inputs needed to rebuild every pipeline without the guest:

| File | Contents |
|---|---|
| `<hash>_<perm>.spv` | Translated SPIR-V |
| `<perm_hash>.meta` | Shader `Info` and its specialization |
| `g_<hash>.key`, `c_<key>.key` | Graphics and compute pipeline keys, plus vertex input state |
| `profile.bin` | The `Shader::Profile`. If the device or driver profile changes, the whole cache is ignored. |

- **Reads.** `PipelineCache::WarmUp()` reads the files in the `PipelineCache` constructor. That runs
  inside `sotcgpu_init`, when the presenter or rasterizer is created. It recreates every cached pipeline
  (`vkCreateShaderModule` and `vkCreate*Pipelines` with `preloading = true`) and logs
  `Preloaded N pipelines`.
- **Writes.** Files are written as each new pipeline is compiled (`RegisterShaderBinary`,
  `RegisterShaderMeta`, `RegisterPipelineData`). The writes are queued to the IO thread
  `shadPS4:PipelineCacheIO`, so the GPU thread only copies a small vector. Nothing is batched and
  nothing waits for shutdown.
- **Archive mode.** `pipeline_cache_archived` (a zip) is written only in `Close()`, which a run killed by
  smoke never reaches. It stays **off**.
- **Driver cache.** The `VkPipelineCache` starts empty and is never saved. On NVIDIA the driver's own disk
  cache covers the `vkCreate*Pipelines` cost on later runs.
- **Shader cache.** There is no separate setting: SPIR-V is part of the same cache. `dump_shaders`,
  `patch_shaders` and `shader_collect` are debug features.

**What sotcgpu now does** (`gpu/src/sotcgpu.cpp`, `sotcgpu_init`):
- `pipeline_cache = true` whenever `sotcgpu_config::cache_dir` is set. The runtime always sets it to
  `$SOTC_USER_DIR/gpu_cache`. On by default since session 21 (`SOTC_GPU_PIPELINE_CACHE=0` turns it off; the old warm-up crash is gone).
- The `test_sotcgpu_*` tests pass no `cache_dir`, so the cache stays off for them.
- `CacheDir` is set to `<cache_dir>/pipelines-v1`. `DataBase::Open` appends the game serial and creates the
  directory.
  - Under smoke, the files go to **`build/user/gpu_cache/pipelines-v1/CUSA08809/`**.
  - A default run (`SOTC_USER_DIR` unset) writes to `user/gpu_cache/...`. That path is also git-ignored,
    because it contains `CUSA*/`.
- `kPipelineCacheVersion` goes into the path. shadPS4 only checks its own serialization versions, so after
  a local `shader_recompiler` patch the old SPIR-V would still load. Bump the constant with such patches;
  the rule is noted in `third_party/shadps4/README.md`.
- `sotcgpu_shutdown` calls `Storage::DataBase::Close()`.

**Patch to `cache_storage.cpp`** (listed in the README's patch table):
1. Atomic writes: each blob goes to `<name>.tmp` and is then renamed into place.
   - Smoke kills the game, and a blob cut short mid-write would make the next `WarmUp` hit an
     `ASSERT` in `Serialization::Reader`, or hand the driver bad SPIR-V.
   - The `.tmp` leftovers are never loaded: their extension matches no blob type.
   - Keys are queued after their shaders, so a kill can leave a key without its shaders, but not the
     reverse. A missing meta or spv only makes that pipeline count as stale.
2. `Close()` runs the requests still queued. Before this, a clean exit dropped them.
3. `num_requests` becomes `std::atomic<u32>`. It was decremented without a lock, and a lost decrement
   would leave the IO thread spinning on an empty queue.

**Expected effect.**
- Run 1 is unchanged, apart from the background file writes.
- From run 2 on, startup pays to rebuild every pipeline seen so far. In exchange, runtime misses (the
  `Compiling graphics pipeline` log lines) disappear for anything already seen, and cuts stop
  translating and compiling.

## 2. Cheap `hle_memory_clamp_range`

`runtime/src/hle/memory.c`. Before this change, every call took `g_lock` and binary-searched the region
table. The GPU thread calls it on every buffer bind.

**Design: a per-thread cache validated by a generation counter.**
- `g_regions_gen` is a `_Atomic uint64_t` that starts at 1. It is bumped (release) in `regions_insert` and
  `regions_erase`, the only places `g_regions` changes. Both run under `g_lock`, and a split goes through
  them too.
  - `mprotect` changes only `prot`, and `clamp_range` ignores `prot`.
- `_Thread_local clamp_cache t_clamp = {gen, lo, span_hi, run_hi}`, filled on a miss under `g_lock` with
  the generation read under the lock:
  - `[lo, span_hi)` is the first span walked. For a region, `lo` is the region's start. For the
    loaded-image span, `lo` is the queried address.
  - `[lo, run_hi)` covers the contiguous mapped spans the walk went through.
  - Holes are never cached.
- **Hit:** `gen` matches the current (acquire) value and `addr >= lo`.
  - An unbounded request (≥ 1 GiB) is answered from `span_hi`, then the cap applies. It keeps the
    first-span-only rule.
  - A bounded request is answered with `size` when `size <= run_hi - addr`.
  - Anything else takes the locked path, which is the same code as before.
- **Correctness:** a hit returns exactly what the locked walk returned at generation `gen`. Any map,
  unmap or split bumps the generation, so every thread's cache misses afterwards.
  - A reader that loaded the old generation just before a concurrent unmap is ordered before that unmap.
    That is the same result as taking the mutex first, and the locked version's answer could go stale
    the moment it unlocked anyway.
- **Cost of a hit:** one TLS access, one atomic load and two compares. No lock is taken.
- `hle_memory_is_gpu_mapping` goes through the same path.

**Tests:** `runtime/tests/test_memory_clamp.c` covers:
- holes
- miss, then hit
- region edges
- adjacent regions: bounded requests cross them, unbounded requests stop at the first
- invalidation after another thread unmaps a range this thread has cached
- remapping smaller at the same address
- a partial unmap (split)
- reserved ranges
- 4000 random map, unmap and query steps checked against a model
- a reader/writer stress: 2000 map/unmap cycles while another thread clamps, where every result must be
  all or nothing, followed by a final-state check

A mutation check (dropping the bump in `regions_erase`) makes the invalidation checks fail.

## 3. Compiling pipelines off the GPU thread: findings and design (not implemented)

**Findings at 14ada48.**
- There is no async compile setting. A miss in `GetGraphicsPipeline` and `GetComputePipeline` does the
  following synchronously on the GPU (command-processor) thread:
  - `RefreshGraphicsKey`/`RefreshComputeKey`, which translate the GCN shaders when the permutation is
    new
  - `vkCreateShaderModule`
  - `vkCreateGraphicsPipelines`/`vkCreateComputePipelines`
- The only "background" pieces are the cache file writes and `WarmUp` (which runs at init, not
  asynchronously).
- When `GetGraphicsPipeline` returns `nullptr`, `Rasterizer::Draw` drops the draw. That is the natural
  hook for "skip until ready".

**Design options, cheapest first.**
1. **Measure first.** Time the miss path. Add a `Common::Timer` around the `make_unique<GraphicsPipeline>`
   in `GetGraphicsPipeline` and around `CompileModule`, and log totals per second. The disk cache above
   should remove most cut stalls. If cuts are still slow on run 2, the cause is elsewhere: buffer or
   texture cache uploads, or readbacks.
2. **Async driver compile, guest-side translation kept synchronous.**
   - Translation reads guest memory (shader code, user data, sharps), so it must stay at draw time. It
     is usually the cheaper half.
   - On a miss, the GPU thread translates, captures the inputs to the `GraphicsPipeline` constructor by
     value (infos, runtime infos, fetch shader, modules, `sdata`), stores a `pending` entry with a
     future in `graphics_pipelines`, and hands `vkCreateGraphicsPipelines` to a small worker pool
     (2–3 threads).
     - `VkPipelineCache` is internally synchronized, and creating different pipelines concurrently is
       legal.
   - Until the future is ready, `GetGraphicsPipeline` returns `nullptr` and the draw is skipped.
   - **SotC risk:** skipped draws feed later passes, and the camera constants are computed on the GPU.
     Only **graphics** draws should be skipped. Compute pipelines must stay synchronous.
   - Bound the skipping. After N frames, or for draws whose render target is later read back, wait on
     the future instead.
   - `DescriptorHeap` and `BuildDescSetLayout` are touched in the constructor, so the layout creation
     stays on the GPU thread and only `createGraphicsPipelineUnique` moves to the worker.
   - Files: `vk_pipeline_cache.{h,cpp}` and `vk_graphics_pipeline.{h,cpp}` (split the constructor into
     `Prepare` on the GPU thread and `Build` on the worker), `vk_rasterizer.cpp` (handle "pending"),
     and a setting `async_pipelines` in the settings shim, default off.
3. **`VK_EXT_graphics_pipeline_library`.** Precompile the vertex-input, pre-raster, fragment and output
   libraries and link them fast on a miss (a fast-link library pipeline), then optimize the full
   pipeline in the background. This is the right long-term fix, and NVIDIA supports it, but it is a
   large change to `GraphicsPipeline`. Leave it for P2 or later.
4. **Run `WarmUp` asynchronously** (compile the cached pipelines on worker threads during the intro) if
   startup grows too long as the cache fills.

## What the main session must check on a GPU run
1. **Run 1** (`smoke.py --exe build-vk/sotc-runtime.exe --gpu vulkan --seconds 120`):
   - `build/user/gpu_cache/pipelines-v1/CUSA08809/` fills with `*.spv`, `*.meta`, `*.key` and
     `profile.bin` during the run, not only at exit.
   - No `Failed to write` errors.
2. **Run 2:**
   - The log shows `Preloaded N pipelines` with N about equal to the number of `.key` files, and no
     "stale" or "not compatible" warning. A few stale pipelines are fine.
   - The number of `Compiling graphics pipeline` lines drops sharply.
   - Startup time grows only modestly.
   - Fps on the cutscene cuts improves.
   - Screenshots match run 1. A mismatch would mean a stale-SPIR-V or preload bug; check it with
     `SOTC_GPU_PIPELINE_CACHE=0`.
3. **Clamp:** a thread profile should no longer show `hle_memory_clamp_range` or `plat_mutex_lock`
   (about 3–4% of the GPU thread before). Rendering should be unchanged.
